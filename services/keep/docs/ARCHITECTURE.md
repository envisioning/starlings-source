# Keep — how it works

The reference for anyone changing Keep's logic, on any client. `README.md`
says what Keep is and what it promises; `AGENTS.md` says how to run and
what must not change; this says how the pieces fit. Written 2026-09-19.

## The key hierarchy

Everything hangs off one rule: **the server holds no key.** Every arrow
below is "wrapped under", and every wrap is made on a client.

```
passkey PRF output ──HKDF──┐
                           ├──▶ wrapping key ──AES-GCM──▶ staff private key (P-256)
passphrase ──PBKDF2──────┘         (one wrap per method; a person may hold both)

staff private key ──ECDH+HKDF──▶ per-member wrapping key ──AES-GCM──▶ vault key (32 bytes)
                                  (one row per member: vault_members.wrapped_key)

recovery private key (split in two shares, held offline) ──same──▶ vault key
                                  (one row per key version: vault_recovery_keys)

vault key ──AES-GCM, AAD = vault:item:version──▶ item body (JSON: username, password, url, notes, totp)
```

What the server stores, per table (`api/migrations/`):

| Table | Plaintext | Sealed |
| --- | --- | --- |
| `staff_keys` | email, name, public key, wrap parameters (salts, credential id) | private key, once per method (`wrapped_private_key` + `extra_wraps`) |
| `recovery_key` | public key, holder emails | nothing — the private half is two shares outside Keep |
| `vaults` | name, icon, `project_id`, key version | nothing |
| `vault_members` | vault, email, key version | vault key, to that member |
| `vault_recovery_keys` | vault, key version | vault key, to the recovery key |
| `items` | name, kind, key version | the body |
| `audit_events` | everything | nothing |
| `device_tokens` | owner, device name, scope, expiry, SHA-256 of the token | nothing |
| `agents` | roster address, name, public key | nothing — the private half is in the broker |

A machine vault (`vaults.machine = 1`) is an agent's own service keys
(ADR 0007). Its only member is the agent. Its items carry `wrapped_key`:
each item has its own key, wrapped to the agent's public key, because no
person holds the vault key.

```
person ──item key (fresh)──AES-GCM, AAD = vault:item:version──▶ item body
person ──agent public key──ECIES──▶ item key            (items.wrapped_key)
broker ──agent private key──▶ item key ──▶ item body    (never keep-api)
```

## The suite (`keep-v1`)

Two implementations, held to the same bytes by
`crypto/src/vectors.json` (generated by TypeScript, opened by
Swift in `core-kit/Tests/KeepKitTests`).

| Operation | Primitive | Where |
| --- | --- | --- |
| Staff keypair | ECDH P-256; public = raw x9.63 point, private = PKCS#8 | `generateStaffKeypair` |
| Wrap to a public key | ephemeral P-256 → ECDH → HKDF-SHA256(salt = ephemeral‖recipient, info = `keep-v1/wrap-to-public-key`) → AES-256-GCM, AAD = recipient public key | `wrapKeyToPublicKey` / `KeepCrypto.wrapKey` |
| Private key by passkey | WebAuthn PRF (salt `keep.org.example/prf/v1`) → HKDF-SHA256(random salt, info `keep-v1/prf-wrapping-key`) → AES-256-GCM, AAD `keep-v1/staff-private-key` | `wrapPrivateKeyWithPRF` |
| Private key by passphrase | NFKC → PBKDF2-SHA256, 600 000 rounds, random salt → AES-256-GCM, same AAD | `wrapPrivateKeyWithPassphrase` |
| Item | AES-256-GCM, 12-byte IV, tag appended, AAD `${vault_id}:${item_id}:${key_version}` | `sealItem` / `openItem` |
| Recovery split | XOR: share A random, share B = key ⊕ A | `splitSecret` |
| One-time codes | RFC 6238 over the sealed `totp` field, client-side | `web/src/totp.ts`, `KeepTOTP` |

Implementations: `crypto/src/index.ts` (browser, Node) and
`core-kit/Sources/KeepKit/KeepCrypto.swift` (CryptoKit). The Worker imports
neither.

## Who is asking

Two credentials, one `StaffSession { sub, email, name }`:

- **Cookie** `keep_session`: an HS256 JWT after Google sign-in
  (`hd = org.example`, email verified), 8 hours. Used by the web SPA.
- **Bearer** `evk_…`: a device token the Meet Worker obtains through
  `POST /api/tokens/meet-exchange` (HMAC over `KEEP_INTERNAL_SECRET`) after
  Meet's own Google sign-in. 90 days, one live token per (owner, device
  name), hashed at rest. Used by the Meet apps.

A session proves identity. It opens nothing; that needs the private key,
which is on the client. No PATs.

A third principal, an **agent**: an `evk_` token with scope `agent`, minted
by the same exchange with `scope: 'agent'` and the agent's Meet roster
address. Meet's signature says the address is on its roster. It reaches
`/api/agent/me`, `/api/agent/key` and its own releases only; every other
path is 404 for it. The broker holds it. The agent's sandbox never
does: for a release, Meet's Worker mints one and fetches for the agent.

## Flows

**Enrol.** Client makes a P-256 keypair, wraps the private half (passkey or
passphrase), `PUT /api/keys/me` with public key + wrapped blob + wrap
params. Re-enrol (`?replace=1`) replaces the key and deletes every
`vault_members` row for that person, because the old wraps are dead.

**Add a way to unlock.** With the key open, client wraps it again under
the other method and `POST /api/keys/me/wraps`. One wrap per method; a
second passphrase replaces the first. `StaffKey.wraps` lists them,
enrolment first. This is how a phone passkey enrolment gets a passphrase
for a client without passkeys.

**Unlock.** Client fetches `/api/me`, picks a wrap it can open (passkey if
the app can use one and the key has one; passphrase if the key has one),
unwraps the private key into memory. Locks after 15 idle minutes, on
hide/quit, never persisted.

**Create a vault.** Client makes a 32-byte vault key, wraps it to itself,
to each chosen colleague (public keys from `/api/keys/directory`), and to
the recovery key if one exists. `POST /api/vaults`. The server refuses a
payload that does not wrap to the caller, wraps to someone not enrolled,
or disagrees with the recovery rule (wrap required once a recovery key
exists, refused before).

**Grant.** Member unwraps the vault key, wraps it to the newcomer,
`POST /api/vaults/:id/members`.

**Revoke = rotate.** There is no delete-member route. The client: reveals
every item, opens each under the old vault key, generates a new vault key,
seals every item under it with `key_version + 1` in the AAD, wraps the new
key to every remaining member and to recovery, `POST /api/vaults/:id/rotate`.
The server applies it in one D1 batch after checking: version is current+1,
every live item is present exactly once, every member is enrolled, the
caller stays. It keeps the previous generation's recovery wrap.

**Reveal.** `GET /api/vaults/:id/items/:item` returns one ciphertext and
writes one `item.reveal` audit row. Rate-limited per person (300/min, so a
rotation of a large vault fits). Lists never carry ciphertext.

**Recovery.** Two people each hold one share of the recovery private key,
made once in a Settings ceremony (`PUT /api/recovery`, set-once). Vaults
made before it are covered by any member on their next unlock
(`POST /api/vaults/:id/recovery`). To recover: a person with both shares
joins them on their device, `GET /api/recovery/vaults` (every covered
vault, wrap sealed to the recovery key; audited), opens the wanted vault's
key, wraps it to their own public key, `POST /api/recovery/vaults/:id/join`
(audited as `recovery.join`, `granted_by = recovery:<email>`). They are
now a member and can rotate whoever else out.

**Machine vault.** Meet brokers an agent token. The broker makes a P-256
pair, keeps the private half, and registers the public half
(`PUT /api/agent/key`, set once). A person picks the agent, makes a vault
key, wraps it to the agent's public key only, `POST /api/machine-vaults`.
To add or rotate an item, a person makes an item key, seals the body under
it with the usual AAD, wraps the item key to the agent's public key, and
sends both. Nobody reads an item through keep-api. **Revoke** an agent:
`POST /api/machine-vaults/:id/revoke` revokes its tokens, drops its
membership and its key, and raises the key version, in one batch. Then a
new token, a new key from the broker, and **Grant again**
(`POST /api/machine-vaults/:id/agent`) at the new version. Old items need
a new value; rotate them at the vendor first.

**Who can use it** (ADR 0007 decision 7). Every vault and item
lists who can use it: people (members of a person's vault), agents with
standing access (a machine vault's agent), and agents with an active
release (on a person's vault only). Each row has its last use, the
newest `item.reveal` or `item.use` by that principal (for a release, its
fetch), and Revoke: a person's removal (rotate), an agent's revoke, or a
release's end. `src/access.ts`, `liveReleases` in `src/releases.ts`.

**Attended release** (ADR 0007 decisions 5 and 10 to 12). An agent
asks in a Meet thread for one item, with a P-256 public key it made for that
request and a request id. A member of the item's vault approves on their
device: it reveals the item (`item.reveal`), opens it, seals the body under
a one-time key with AAD `release:${release_id}:${vault_id}:${item_id}`,
wraps that key to the agent's session key, and `POST /api/vaults/:id/releases`
with the request id as the release id (`release.approve`). The named agent
fetches the payload once before the expiry (`item.use`); the fetch clears it.
Any member ends it early (`release.end`); the end clears it too. The body,
not a key: a person's vault key opens every item, so wrapping it would
release the vault. `src/releases.ts`.

**Project vaults.** A vault may carry a Core `project_id`. Meet's Work
opens "Keep vault" on a project: `KeepSession.ensureVault(forProject:)`
finds the member's vault with that id or creates one named after the
project. Keep never resolves the id; Core's page is a link out.

## Routes

| Method | Path | Auth | Does |
| --- | --- | --- | --- |
| GET | `/api/health` | none | liveness |
| GET | `/api/auth/google/start`, `/callback` | none | web sign-in |
| POST | `/api/auth/logout` | cookie | clears the cookie |
| POST | `/api/tokens/meet-exchange` | HMAC | mints a device token |
| GET | `/api/me` | any | session + own `StaffKey` |
| PUT | `/api/keys/me[?replace=1]` | any | enrol / re-enrol |
| POST | `/api/keys/me/wraps` | any | add or replace a wrap |
| GET | `/api/keys/directory` | any | everyone's public key |
| GET / PUT | `/api/recovery` | any | recovery public key (set once) |
| GET | `/api/recovery/vaults` | any (audited) | every covered vault with its recovery wrap |
| POST | `/api/recovery/vaults/:id/join` | any (audited) | become a member with a wrap made through recovery |
| POST | `/api/vaults/:id/recovery` | member | add the missing recovery wrap |
| GET / DELETE | `/api/tokens[/:id]` | any | own device tokens |
| GET | `/api/audit` | any | recent events, all vaults |
| GET / POST | `/api/vaults` | any | list mine / create |
| GET / PATCH / DELETE | `/api/vaults/:id` | member | detail (members, items, no ciphertext) / name, icon, project / delete |
| POST | `/api/vaults/:id/members` | member | grant |
| POST | `/api/vaults/:id/rotate` | member | revoke by rotation |
| GET | `/api/vaults/:id/audit` | member | this vault's trail |
| POST | `/api/vaults/:id/items` | member | create (client-chosen id) |
| GET / PATCH / DELETE | `/api/vaults/:id/items/:item` | member | reveal (audited, limited) / update / delete |
| GET | `/api/vaults/:id/access[?item=]` | member | who can use it: people, with last use, and live releases |
| POST | `/api/vaults/:id/releases` | member | approve a release: the sealed body and the wrap to the agent's session key |
| GET | `/api/vaults/:id/releases/:rid` | member | one release's state, never its payload |
| POST | `/api/vaults/:id/releases/:rid/end` | member | end it now (audited once) |
| GET | `/api/machine-vaults/:id/access[?item=]` | person | who can use it: the agent, with last use |
| GET | `/api/agents` | person | agents Keep knows: address, name, public key, vault |
| GET / POST | `/api/machine-vaults` | person | every machine vault / create one for an agent |
| GET | `/api/machine-vaults/:id` | person | detail (items as names, no ciphertext, no wrap) |
| POST | `/api/machine-vaults/:id/agent` | person | grant the agent again after a revoke |
| POST | `/api/machine-vaults/:id/revoke` | person | end the agent's standing access |
| GET | `/api/machine-vaults/:id/audit` | person | this vault's trail |
| POST | `/api/machine-vaults/:id/items` | person | add, sealed to the agent |
| PATCH / DELETE | `/api/machine-vaults/:id/items/:item` | person | rename or new value / delete. No GET. |
| GET | `/api/agent/me` | agent | itself and its vault, names and counts |
| PUT | `/api/agent/key` | agent | the broker registers the agent's public key (set once) |
| GET | `/api/agent/releases/:id` | agent (named) | one of its releases: state only |
| POST | `/api/agent/releases/:id/fetch` | agent (named) | the payload, once, before the expiry; 410 after |
| GET | `/.well-known/apple-app-site-association` | none | names the Meet app for passkeys |

"member" means `requireMembership`: a `vault_members` row for the caller,
else 404. It never matches a machine vault. "person" is any cookie or
`person` token; "agent" is an `agent` token, which reaches its own routes
only. Every non-GET from a cookie must carry the web Origin; a bearer is
exempt (a device has no ambient credential to forge).

## Clients

| | Web SPA (`web/`) | Meet apps (`core-kit` KeepKit + KeepUI) |
| --- | --- | --- |
| Identity | cookie | device token via Meet Worker |
| Key in memory | `session.ts` module state | `KeepSession` (`@MainActor`, ObservableObject) |
| Passkeys | WebAuthn PRF | `ASAuthorization` PRF; needs the `webcredentials:` associated domain in the app's signature (see `meet/docs/KEEP.md`) |
| Only here | recovery ceremony, 1Password import | project vault door, QR by camera |

Both clients hold plaintext only in the view that shows it and drop it on
close. Neither writes a key or a body to storage.

## Changing things

- A new sealed field: add it to `itemBodySchema` (contracts) and
  `KeepItemBody` (Swift) with a default; old bodies keep opening.
- A new plaintext column: migration, contract type, `toSummary` in
  `vaults.ts`/`items.ts`, Swift model. Ask first whether it must be
  plaintext — the server needs it only to list, route or audit.
- A change to the suite: bump `CRYPTO_SUITE`, regenerate `vectors.json`
  (`node --experimental-strip-types crypto/scripts/vectors.ts`),
  copy it to `core-kit/Tests/KeepKitTests/Fixtures/`, make both test suites
  pass, then decide how existing rows migrate. There is no server-side
  re-encryption; only clients can.
